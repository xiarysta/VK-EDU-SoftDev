# Задание №6

## Границы MVP

uTravel — внутренний B2B-сервис для туристических агентств. Цель MVP — проверить, помогает ли сервис менеджеру быстрее подготовить индивидуальный маршрут и контролировать бюджет поездки.

В объём работы входят функции из MVP в ДЗ №3: авторизация (US-02), ввод параметров поездки (US-04), генерация маршрута по дням (US-05), подбор жилья, питания и развлечений с предполагаемой стоимостью (US-06), редактирование маршрута (US-07), пересчёт расходов и предупреждение о превышении бюджета (US-08), сохранение и повторное открытие маршрутов (US-09).

На пилоте учётные записи создаются вручную через административную панель Django, а менеджер переносит готовый маршрут в привычный документ для клиента. Самостоятельная регистрация, оплата подписки, выгрузка PDF, карта и учёт партнёрских комиссий в объём этого MVP не входят.

## Hiring Plan — команда для MVP

Выбираем небольшую кросс-функциональную команду: специалисты вместе отвечают за весь сценарий подготовки маршрута, от требований до запуска пилота. Виртуальная команда состоит из пяти постоянных участников и DevOps-инженера с частичной занятостью.

| Роль | Главная зона ответственности №1 | Главная зона ответственности №2 |
| --- | --- | --- |
| **Product Manager / Product Owner** | Определяет цель MVP и приоритеты бэклога, собирает обратную связь менеджеров пилотных агентств. | Совмещает организацию поставки и обязанности Scrum-мастера: проводит встречи, помогает устранять препятствия и отслеживает риски. |
| **UX/UI Designer с функциями аналитика** | Уточняет сценарии менеджера и критерии приёмки: ввод параметров, работа с маршрутом и контроль бюджета. | Проектирует форму поездки и редактор маршрута, проверяет понятность интерфейса с представителями агентств. |
| **Frontend Developer** | Реализует интерфейс на React + TypeScript: авторизацию, форму параметров, просмотр и редактирование маршрута. | Связывает интерфейс с Django API, отображает состояние генерации, ошибки и изменения стоимости. |
| **Backend Developer / Tech Lead** | Реализует Django REST API и хранение в PostgreSQL: доступ к данным агентства, маршруты, сохранение изменений и расчёт стоимости. | Отвечает за технические решения и интеграцию с Plantrip API: запуск генерации, получение статуса и обработку ошибок внешнего сервиса. |
| **QA Engineer** | Проверяет основной сценарий MVP и случаи ошибок: некорректные даты, неизвестная стоимость, превышение бюджета и сбой генерации. | Проверяет взаимодействие интерфейса, API и базы данных, а также сохранность маршрута и изоляцию данных агентств перед выпуском. |
| **DevOps Engineer — частичная занятость** | Настраивает сборку и развёртывание React и Django через Gunicorn + Nginx, HTTPS и хранение секретов окружения. | Настраивает журналы ошибок и резервное копирование PostgreSQL для сопровождения пилота. |

Отдельный ML Engineer для MVP не требуется: генерацию выполняет внешний Plantrip API, выбранный в ДЗ №5. Настройку базы данных и базовые проверки безопасности выполняют Backend Developer и DevOps Engineer в рамках своих зон ответственности.

## Development Framework — Scrum

Выбираем **Scrum со спринтами по две недели**.

1. **Требования будут уточняться на пилоте.** После каждого спринта можно показать менеджерам агентств работающую часть сценария, собрать обратную связь по маршруту и бюджету и изменить приоритеты следующих работ.
2. **Есть техническая неопределённость.** Интеграцию с внешней генерацией проверяем в первых спринтах: получение результата, время ожидания, полноту цен и обработку сбоев. Короткие циклы позволяют обнаружить проблемы до подготовки всего MVP.
3. **Нужен общий результат нескольких специалистов.** Цель спринта объединяет работу дизайнера, frontend, backend и QA вокруг проверяемой пользовательской возможности. Например, менеджер вводит параметры и получает сохранённый маршрут по дням через интерфейс сервиса.

Product Manager выполняет роль Product Owner и на время MVP совмещает её с обязанностями Scrum-мастера. Остальные специалисты образуют команду, создающую продукт; DevOps участвует в работах по инфраструктуре и выпуску по мере необходимости.

**Product Backlog** содержит упорядоченные истории и технические задачи в границах MVP. На планировании команда выбирает цель спринта и формирует **Sprint Backlog**. Результат спринта — работающий, проверенный прирост продукта, который можно продемонстрировать агентствам.

Задача считается готовой, когда выполнены её критерии приёмки, код прошёл проверку другим разработчиком, QA проверил соответствующий сценарий, а изменение развёрнуто на тестовом стенде. Для сценария генерации проверяется вся цепочка: ввод параметров, ответ внешнего сервиса, отображение результата и сохранение маршрута. Неизвестные цены должны оставаться явно отмеченными, а расчёт расходов — обозначаться как неполный.

## Team Rituals — обязательные встречи

| Встреча | Цель | Частота | Участники |
| --- | --- | --- | --- |
| **Планирование спринта** | Согласовать цель спринта, выбрать задачи из Product Backlog и учесть зависимости между интерфейсом, сервером и внешним API. | Раз в две недели, в начале спринта; до 1 часа. | Product Owner и команда; DevOps при наличии инфраструктурных задач. |
| **Ежедневный Scrum** | Проверить продвижение к цели спринта и согласовать ближайшие действия. Например, если интеграция заблокирована, договориться о совместной проверке ответа внешнего API. | Каждый рабочий день; 15 минут. | Команда, создающая продукт; Scrum-мастер при необходимости помогает снять препятствия. |
| **Уточнение бэклога** | Разобрать ближайшие истории, уточнить критерии приёмки, выявить неизвестные и разделить слишком крупные задачи до следующего планирования. | Раз в неделю; до 45 минут. | Product Owner, дизайнер-аналитик, разработчики и QA; DevOps при необходимости. |
| **Обзор спринта** | Показать работающий результат представителям пилотных агентств, проверить удобство подготовки маршрута и собрать обратную связь для бэклога. | Раз в две недели, в конце спринта; до 45 минут. | Product Owner, команда и представители пилотных агентств. |
| **Ретроспектива спринта** | Обсудить, что мешало поставке и взаимодействию, и выбрать конкретное улучшение процесса на следующий спринт. | Раз в две недели, после обзора спринта; до 30 минут. | Product Owner, Scrum-мастер и команда; при совмещении ролей это один участник. |

Решения по требованиям и результаты обратной связи фиксируются в бэклоге. Блокирующие проблемы обсуждаются сразу после обнаружения, чтобы команда могла продолжить работу, не ожидая очередной встречи.
